# web-nav 代码讲解：一次点击的完整流程

这份文档默认你已经读过之前对参考项目 urlNavigation 的分析，知道扩展宿主、贡献点、Disposable、TreeDataProvider、Webview 这些概念。所以这里不再重复讲“是什么”，只讲：**用户点一下侧边栏里的网站，代码从头到尾是怎么走的，以及和参考项目相比哪里改了、为什么改。**

凡是对应之前问题清单 ❶–❽ 的地方，都用同一个格式写：**原项目 → 现在 → 为什么**。

> 行号对应当前这一版代码。以后代码改了，行号可能会偏几行，按函数名搜索即可。

## 总览：这次点击经过哪些文件

```
package.json（声明有哪些视图、命令、菜单、设置项）
  → extension.ts      激活，把各个零件组装起来
  → sites.ts          从设置里读出“我的网站”
  → siteTree.ts       把数据画成侧边栏的树
  → （用户点击）webNav.open 命令
  → embedChecker.ts / embedCheck.ts   判断这个网站能不能放进 iframe
  → sitePanel.ts      创建或复用唯一的 Webview 标签页
  → html.ts + media/  生成页面（iframe 或说明页）
  → 说明页上的链接 → 消息 → commands.ts 里的命令
```

## 1. 清单：package.json

[package.json](../package.json) 是插件的“说明书”，VS Code 不用运行你的代码，光读它就知道插件贡献了什么。

- 入口：[package.json:22](../package.json#L22) `"main": "./dist/extension.js"`，这是 esbuild 打包出来的文件（第 9 节讲）。
- 最低版本：[package.json:8](../package.json#L8) 起的 `engines.vscode`。
- 设置项：[package.json:24](../package.json#L24) 的 `configuration`，定义了 `webNav.sites`（我的网站列表）和 `webNav.showRecommended`（是否显示推荐分组）。
- 侧边栏容器和视图：[viewsContainers，第 50 行](../package.json#L50)、[views，第 59 行](../package.json#L59)，视图 id 是 `webNav.sites`。**只有一个视图**，推荐和我的网站是同一棵树里的两个分组。
- 命令：[commands，第 67 行](../package.json#L67)，全部带 `webNav.` 前缀和“网站导航”分类。
- 菜单：[menus，第 116 行](../package.json#L116)，三块：
  - [commandPalette，第 117 行](../package.json#L117)：把只能在右键菜单或树节点上用的命令设成 `when: false`，不在命令面板里露出来（因为它们需要一个“目标网站”参数，从命令面板调用没有意义）。
  - [view/title，第 147 行](../package.json#L147)：标题栏的 ＋ 和 ⟳ 按钮。
  - [view/item/context，第 159 行](../package.json#L159)：右键菜单，用 `viewItem == site.mine` / `site.recommended` 区分“我的网站”和“推荐网站”，各自显示不同的菜单项。这个 `viewItem` 来自树节点的 `contextValue`（第 4 节）。

### ❶ 依赖放错了位置

- **原项目**：`vsce` 写在 `dependencies` 里，`content-type`、`follow-redirects` 也在 `dependencies`——可它们已经被 webpack 打进了 `dist/extension.js`，运行时根本不需要。
- **现在**：[package.json:213](../package.json#L213) 起只有 `devDependencies`，**没有 `dependencies` 这一段**。运行时唯一需要的 `vscode` 模块由 VS Code 提供；联网用的是 Node 自带的全局 `fetch`，不需要任何第三方库。打包工具（esbuild、`@vscode/vsce` 通过 `npx` 临时下载）都不进运行时依赖。
- **为什么**：`dependencies` 表示“运行时必需”。放错了会让人误以为插件需要它们，也会让 `vsce package` 的检查和体积分析变得混乱。**能不引入的依赖就不引入**，是插件项目最省心的原则。

### ❽（一部分）activationEvents 和各种 ID

- **原项目**：`"activationEvents": ["*"]`，VS Code 一启动就激活它，哪怕你一整天都没点开侧边栏；命令 ID 叫 `itemClick`，没有前缀；5 个视图 id（`read`、`interview` 等）在 package.json、`initTreeViewItem`、`website.ts` 三个地方各写一遍。
- **现在**：
  - package.json 里**根本没有 `activationEvents`**。VS Code 1.74 之后，会根据 `contributes` 自动推断：用户展开 `webNav.sites` 视图，或者执行任何一个 `webNav.*` 命令时才激活。所以这里依赖 `engines.vscode` 足够新（[第 8 行](../package.json#L8) 起是 `^1.103.0`）。
  - 命令 ID 全部是 `webNav.xxx`（命令 ID 是全局命名空间，加前缀避免和别的插件冲突）。
  - 视图 id 只有一个 `webNav.sites`，在 package.json（[第 62 行](../package.json#L62)）和 [extension.ts:20](../src/extension.ts#L20) 里各出现一次；`CONFIG_SECTION = 'webNav'` 在 [sites.ts:8](../src/sites.ts#L8) 里定义一次，读取设置的地方都引用它（package.json 里的配置键和命令 ID 仍是字面量）。
- **为什么**：按需激活让插件不拖慢 VS Code 启动；带前缀的 ID 不会撞车；“同一个字符串散落在几处”是日后改名时最容易漏改的地方。
- **诚实的补充**：命令 ID 字符串（比如 `'webNav.open'`）在代码里仍然出现了不止一次（[extension.ts:21](../src/extension.ts#L21)、[siteTree.ts:92](../src/siteTree.ts#L92)），没有抽成常量。这是一个可以继续改进的小地方，测试 [extension.test.ts:9](../src/test/extension.test.ts#L9) 会帮你兜底——命令少注册了一个就会失败。

## 2. 激活和 Disposable：extension.ts

整个入口只有 [46 行](../src/extension.ts)，它只做“组装”，不放业务逻辑。

[extension.ts:9](../src/extension.ts#L9) `activate` 依次做了几件事：

1. [第 10–12 行](../src/extension.ts#L10)：创建 `EmbedChecker`（嵌入检测器）、`FaviconChecker`（图标探测器，第 4 节）和 `SiteTreeProvider`（树数据源）。两个检测器都**传给**树，而不是树自己去 new——这叫依赖注入，后面测试时可以换成假的（第 8 节）。
2. [第 16–36 行](../src/extension.ts#L16)：把需要释放的东西一次性放进 `context.subscriptions`：两个检测器、树数据源、树视图本身、`webNav.open` 命令。插件被停用时，VS Code 会自动对它们调用 `dispose()`。
3. [第 38 行](../src/extension.ts#L38)：`registerCommands` 注册其余 8 个命令（第 5 节）。
4. [第 40–43 行](../src/extension.ts#L40)：激活后**在后台**检测所有“我的网站”，不 `await`。

### ❺ 监听器重复注册

- **原项目**：[webView.ts:43](../../urlNavigation/src/classes/webView.ts) 的 `onDidDispose` 写在 `if/else` 的外面，每点一次网站就多注册一个监听；`extension.ts` 里每次点击还把同一个 panel 又 `push` 进 `context.subscriptions` 一次。
- **现在**：监听器只在**创建面板的那个分支里**注册一次——[sitePanel.ts:34](../src/sitePanel.ts#L34) 的 `onDidDispose` 和 [sitePanel.ts:40](../src/sitePanel.ts#L40) 的 `onDidReceiveMessage`，都在 `else` 里面（[第 19 行](../src/sitePanel.ts#L19) 起）。再次点击别的网站走的是 `if (instance)` 分支，只 `reveal`，不重复注册。注册时第三个参数传 `context.subscriptions`，让它们随插件一起释放。命令的 handler 也不再往 `subscriptions` 里塞 panel。
- **为什么**：重复注册不会报错，只会悄悄变慢、重复触发。判断标准很简单：**“只需要一次”的事情，必须放在“只发生一次”的位置。**

### 后台检测：为什么不 await

[第 40–43 行](../src/extension.ts#L40) 是计划阶段新增的决定：**激活后在后台检测**。`void checker.check(...)` 发起请求但不等待，所以激活本身是瞬间完成的；检测结果陆续回来时，树视图会自动刷新出 ⚠ 标记（第 4 节）。如果这里 `await` 了，每个网站最多 8 秒的超时会让激活卡住。代价是：刚激活的几秒内，标记可能还没出现——这是可以接受的。

## 3. 设置项的读写：sites.ts

用户的网站列表存在 VS Code **设置**里（`webNav.sites`），而不是插件私有的 `globalState`。好处：用户能在 settings.json 里直接看、直接改，也能被 Settings Sync 同步。代价：用户可能手写出各种奇怪数据，所以**读出来的东西一律不信任**。

[sites.ts](../src/sites.ts) 分成两半：

**纯函数（不依赖 vscode，可以直接单元测试）**：
- [normalizeUrl，第 13 行](../src/sites.ts#L13)：去空格；不带协议就补 `https://`（[第 19–21 行](../src/sites.ts#L19)）；只接受 http/https；其余返回 `undefined`。这就是计划阶段的决定“**不带协议时补 https**”：用户输入 `www.runoob.com` 就能用。判断“有没有协议”用的是 `includes('://')`，而不是 `scheme:` 之类的通用正则，因为 `a.com:8080` 看起来就像 `a.com:` 开头的“协议”。
- [sanitizeSites，第 43 行](../src/sites.ts#L43)：把设置里读出来的 `unknown` 清洗成 `Site[]`。非数组返回空；坏条目（不是对象、没有 url、url 无效）直接跳过；名称为空时用主机名顶上（[第 61 行](../src/sites.ts#L61)）。
- [findSite，第 67 行](../src/sites.ts#L67)：按**规范化后的 url**查找。`https://a.com` 和 `https://a.com/` 会被视为同一个。

**读写设置（依赖 vscode）**：
- [getUserSites，第 77 行](../src/sites.ts#L77)：`getConfiguration('webNav').get('sites')` 再交给 `sanitizeSites`。
- [saveUserSites，第 82 行](../src/sites.ts#L82)：`update('sites', sites, ConfigurationTarget.Global)`——写到用户级设置，不写到工作区。
- [isRecommendedVisible，第 88 行](../src/sites.ts#L88)：读 `showRecommended`。

### ❸ 用 label 当 ID 回查

- **原项目**：[treeViewProvider.ts](../../urlNavigation/src/classes/treeViewProvider.ts) 里树节点点击时只把 `label` 字符串作为命令参数；图标要靠 `website.filter(item => item.label === label)` 再去查一遍；Webview 那边又把**整个网站数组**连同 label 一起 `postMessage` 过去，由 `iframe.js` 再按 label 查出网址。两个网站重名，就会查到错误的那个。
- **现在**：全程传**数据对象**，不传 label。树节点是一个带类型的联合类型 [TreeNode，siteTree.ts:10](../src/siteTree.ts#L10)，网站节点里直接带着 `site`（名称 + 网址）和 `source`（来自“我的”还是“推荐”）；点击命令的参数就是这个节点本身（[siteTree.ts:92](../src/siteTree.ts#L92) 的 `arguments: [node]`）；`SitePanel.show` 接收的也是 `site` 对象（[sitePanel.ts:15](../src/sitePanel.ts#L15)），页面里的网址由插件直接写进 HTML。需要“按身份找条目”时（重命名、移除），用的是**规范化后的网址**，见 [findSite](../src/sites.ts#L67) 和 [commands.ts:142](../src/commands.ts#L142)，网址在“我的网站”里是唯一的（添加时会判重）。
- **为什么**：把 label 当 ID 是“用显示用的字符串当主键”，名称一重复、一改名就坏。**传对象**比“传 key 再回查”更简单也更不容易出错；真的需要 key 时，选一个**天然唯一**的字段（这里是网址）。

## 4. 树视图：siteTree.ts

[SiteTreeProvider](../src/siteTree.ts#L21) 实现了 `TreeDataProvider`，把“数据”变成“侧边栏上的行”。

### 节点类型

[TreeNode（第 10–14 行）](../src/siteTree.ts#L10) 有四种：`group`（我的网站 / 推荐）、`category`（推荐里的子分类）、`site`、`empty`（没有任何网站时的提示行）。用 `kind` 字段区分，TypeScript 在 `switch` 里会帮你检查有没有漏掉分支。

### getChildren / getTreeItem

- [getChildren，第 53 行](../src/siteTree.ts#L53)：根层是“我的网站”，若 `showRecommended` 为真再加“推荐”（[第 55–59 行](../src/siteTree.ts#L55)）；“推荐”下面是 `RECOMMENDED` 里的分类（[recommended.ts](../src/recommended.ts)）；“我的网站”下面是用户的网站，没有时给一个 `empty` 节点（[第 65–68 行](../src/siteTree.ts#L65)）。
- [getTreeItem，第 76 行](../src/siteTree.ts#L76)：
  - `empty` 节点点了会执行 `webNav.addSite`（[第 85 行](../src/siteTree.ts#L85)），空列表本身就是一个引导。
  - `site` 节点：设置 `contextValue = 'site.mine' | 'site.recommended'`（[第 91 行](../src/siteTree.ts#L91)），右键菜单靠它区分；设置点击命令（[第 92 行](../src/siteTree.ts#L92)）；如果检测结果是 `blocked` 或 `insecure`，在行尾显示 ⚠，并把原因写进 tooltip（[第 93–99 行](../src/siteTree.ts#L93)）。原因文案来自 [html.ts 的 REASON_TEXT](../src/html.ts#L36)，说明页和 tooltip 共用一份，不会写出两种说法。

### 刷新是怎么触发的

[构造函数第 29–42 行](../src/siteTree.ts#L29) 订阅了三个事件：检测器的结果更新（⚠ 出现）、favicon 探测完成（图标从地球换成网站自己的）、设置变化（`onDidChangeConfiguration`，且 `affectsConfiguration('webNav')`）。任何一个发生，都调用 [refresh](../src/siteTree.ts#L44) 触发 `onDidChangeTreeData`。

这意味着：**命令不需要手动刷新树**。`addSite` 只要把新列表写进设置，设置变化事件就会让树自己重画。（参考项目的 `onDidChangeTreeData` 压根没实现，数据改了也不会刷新。）订阅对象收集在 [subscriptions 数组](../src/siteTree.ts#L24)，[dispose](../src/siteTree.ts#L48) 里统一释放。

### 依赖注入，方便测试

[构造函数第 29 行](../src/siteTree.ts#L29) 的第三个参数 `deps` 让测试可以传入假的“读设置”函数，不依赖真实设置。见第 8 节。

### favicon 的处理方式

spec 第 5.1 节要求：拿不到网站图标时回退到 Codicon，而第 8 节只把“怎么获取”留给实现者决定。做法是：**默认显示地球图标，探测通过后才换成网站自己的图标**（[siteTree.ts:100–111](../src/siteTree.ts#L100)）。

- **为什么要探测**：直接把 `origin/favicon.ico` 设成图标，遇到 404 或者返回 HTML 页面的网站就是一个空白图标（推荐名单里就有好几个）。VS Code 不会替我们回退，所以必须自己先确认图标可用。
- **纯逻辑**：[favicon.ts](../src/favicon.ts#L1) 和 embedCheck.ts 一样不 import vscode、注入假 fetch。[faviconUrlOf](../src/favicon.ts#L10) 取网址的 `origin/favicon.ico`；[probeFavicon](../src/favicon.ts#L19) 发 GET，**只有 `res.ok` 且 content-type 以 `image/` 开头才算可用**（有的网站对不存在的图标返回 200 + text/html，只看状态码会被骗），带 5 秒超时，任何异常都按“不可用”处理。
- **带缓存的包装**：[FaviconChecker](../src/faviconChecker.ts#L5) 与 EmbedChecker 同一套路——`cached` / `check` / `onDidChange` / `dispose`，同一个地址并发只请求一次，结果（可用或不可用）都缓存，所以每个站点只探测一次。
- **树里的用法**（[siteTree.ts:104–110](../src/siteTree.ts#L104)）：已缓存且可用就换成远程 Uri；还没探测过就 `void check(...)` 后台发起（不等待）；探测结果出来后 `onDidChange` 触发树刷新（[构造函数订阅，第 35 行](../src/siteTree.ts#L35)），这一次就能读到缓存。探测失败也有缓存，所以不会反复请求。
- ⟳ 刷新时 [`favicons.clear()`](../src/commands.ts#L107) 与 `checker.clear()` 一起清缓存，下次渲染重新探测。


### ❸（再次）

参考项目的图标靠 label 查到文件名再用 `Uri.file(join(__filename, ...))` 拼本地路径；现在图标来自网址本身，不依赖任何本地文件，网站再多、用户加什么都不用你准备图标。

### ❽（再一部分）`website.map` 当 forEach、`childs: any`

- **原项目**：[getChildren](../../urlNavigation/src/classes/treeViewProvider.ts) 里 `let childs: any = []`，再用 `website.map(...)` 只为了往里 `push`，`map` 的返回值被丢弃。
- **现在**：返回值有明确类型 `TreeNode[]`，需要转换数据时用 `map` 并直接 `return`（[第 63 行](../src/siteTree.ts#L63)、[第 67 行](../src/siteTree.ts#L67)、[第 71 行](../src/siteTree.ts#L71)）。
- **为什么**：`map` 的意思是“把每个元素变成另一个东西，得到新数组”；只想遍历用 `for...of`/`forEach`。用 `any` 等于关掉类型检查，写错字段名也不会报错。

## 5. 命令和菜单：extension.ts + commands.ts

### 打开命令（本流程的主角）

[extension.ts:21–35](../src/extension.ts#L21) 的 `webNav.open`：

```ts
if (node?.kind !== 'site') { return; }                       // 分组、空提示忽略
const seq = ++openSeq;                                       // 记下这是第几次点击
const verdict = checker.cached(url) ?? await withProgress(() => checker.check(url));
if (seq !== openSeq) { return; }                              // 等待期间又点了别的网站，这次作废
SitePanel.show(context, node.site, node.source, verdict);
```

- 有缓存就直接用，没缓存就先检测再决定显示什么（[第 29–30 行](../src/extension.ts#L29)）。这就是“打开网站时如果还没有检测结果就先检测”的实现。推荐网站不会预先检测，所以第一次点击时可能要真的等（最多 8 秒）。
- **等待时要有反馈**：真正需要等待时，用 `withProgress({ location: { viewId: 'webNav.sites' } }, ...)` 在树视图上显示进度条（[第 30 行](../src/extension.ts#L30)），否则用户点了没反应，会以为点击没生效。有缓存时不经过它，所以不会闪一下进度条。
- **后一次点击覆盖前一次**：[`openSeq`（第 14 行）](../src/extension.ts#L14) 是点击序号，每次点击先 `++openSeq` 记下自己的号码（[第 26 行](../src/extension.ts#L26)），`await` 回来后如果号码已不是最新的就直接放弃（[第 31–33 行](../src/extension.ts#L31)）。没有它会出现这样的错乱：先点了慢网站 A（还在检测），再点已有缓存的 B，B 立即打开；等 A 的检测终于结束，面板又跳回 A。有了序号，永远以**最后一次点击**为准。
- 然后把 `site`、`source`、`verdict` 一并交给面板。

### 管理命令：commands.ts

[registerCommands，第 69 行](../src/commands.ts#L69) 里的小工具 [`register`（第 70–71 行）](../src/commands.ts#L70) 统一加 `webNav.` 前缀，并且自动 `push` 进 `context.subscriptions`。

| 命令 | 位置 | 要点 |
| --- | --- | --- |
| `addSite` | [第 76 行](../src/commands.ts#L76) | 输网址 → 判重 → http 尝试升级 https → 输名称 → 保存 → 后台检测 |
| `refresh` | [第 105 行](../src/commands.ts#L105) | 清缓存，并发重新检测，刷新树 |
| `openInBrowser` / `copyUrl` | [第 115 行](../src/commands.ts#L115)、[第 122 行](../src/commands.ts#L122) | 简单 |
| `rename` | [第 130 行](../src/commands.ts#L130) | 按网址重新定位再改名 |
| `editUrl` | [第 151 行](../src/commands.ts#L151) | 与自己相同不算重复 |
| `remove` | [第 188 行](../src/commands.ts#L188) | **先确认**再删，返回是否真的删了 |
| `addRecommended` | [第 210 行](../src/commands.ts#L210) | 把推荐网站加到“我的网站” |

几个值得细看的设计：

**1. 同一个命令，两种来源的参数。** 右键菜单传的是树节点，说明页传的是普通 `Site`。[toSite，第 12–20 行](../src/commands.ts#L12) 统一取出 `Site`，命令本身不用关心谁调用它。

**2. 输入校验。** [askUrl，第 25 行](../src/commands.ts#L25) 用 `showInputBox` 的 `validateInput` 在输入过程中就提示错误（[第 32 行](../src/commands.ts#L32)）；[askName，第 38 行](../src/commands.ts#L38) 不允许空名称。

两个输入框还各设了两项，都来自验收时真实遇到的困惑：添加网站要先后弹出两个输入框，第二个在窗口顶部不太显眼，而 `showInputBox` 默认一旦失去焦点（点了侧边栏或别处）就会自动关闭，等于取消，结果网站没加上也没有任何提示。

- `title`（[第 27 行](../src/commands.ts#L27)）：由调用者传入，添加时显示“添加网站（1/2）”“添加网站（2/2）”，让人知道后面还有一步。重命名、修改网址则显示各自的标题。
- `ignoreFocusOut: true`（[第 31 行](../src/commands.ts#L31)）：点到别处也不关闭。比如先打开输入框，再切到浏览器去复制网址，回来时输入框还在。

**3. “保存前重新读取”。** 看 [saveFresh，第 59–67 行](../src/commands.ts#L59)：

```ts
const sites = getUserSites();      // 保存的那一刻，重新读一遍最新设置
if (!change(sites)) return false;  // 由调用者在最新列表上做修改
await saveUserSites(sites);
```

这是一个真实踩过的坑：用户点了“修改网址”，弹出输入框，**在等待输入、等待网络的几秒里，设置可能已经被别的操作改过**（比如用户同时在 settings.json 里改了，或者另一个命令加了网站）。如果用最开始读到的旧快照去覆盖，别人的改动就丢了。所以每个写操作都是“输入完之后，重新读 → 按网址找到目标 → 修改 → 保存”。可以对照 [addSite 第 92–99 行](../src/commands.ts#L92)、[rename 第 141–148 行](../src/commands.ts#L141)、[editUrl 第 170–182 行](../src/commands.ts#L170)、[remove 第 200–207 行](../src/commands.ts#L200)。找不到条目（已被删）就静默放弃。

**4. 先快速判重，再最终判重。** [addSite 第 82 行](../src/commands.ts#L82) 在输入网址后立刻判重，让用户少填一步名称；但真正有效的判重在保存前（[第 93 行](../src/commands.ts#L93)），因为升级成 https 之后网址可能变得重复了。

**5. http 升级。** [upgradeWithProgress，第 49 行](../src/commands.ts#L49)：只有 `http://` 才会发请求（所以才显示进度条），内部调用 [tryUpgradeToHttps](../src/embedCheck.ts#L52)：https 版本能响应就换成 https，否则保持原样。原因在 spec：Webview 里的 iframe 不能加载 http 页面（混合内容被拦截）。

**6. 移除前确认。** 这是计划阶段新增的决定。[remove，第 194–195 行](../src/commands.ts#L194) 用 `showWarningMessage(..., { modal: true }, '移除')` 弹模态对话框；只有用户点了“移除”才继续（[第 196 行](../src/commands.ts#L196)）。返回 `boolean` 是为了让说明页知道“真的删掉了”才关闭面板（第 7 节）。

**7. 后台检测。** [`checkInBackground`，第 74 行](../src/commands.ts#L74) 写成 `void checker.check(url)`——不等待。注释里说明了原因：`check` 内部吞掉了所有异常，永远不会 reject，所以不用 `await` 也不会留下未处理的错误。

### ❽（再一部分）命令 ID

参考项目的 `itemClick`（无前缀）和 `registerCommand` 的回调里再 `push` panel，在这里都没有了：命令一律 `webNav.xxx`，注册由 [`register`](../src/commands.ts#L70) 统一包装。

## 6. 嵌入检测：embedCheck.ts 与 embedChecker.ts

这是整个插件最“有想法”的部分：**在打开网站之前，先判断它的服务器允不允许被 iframe 嵌入**。你已经知道原理——`X-Frame-Options` 和 CSP `frame-ancestors` 会让浏览器拒绝渲染；问题是 iframe 被拒绝时是一片空白，用户不知道为什么。所以我们提前自己检查响应头，不能嵌入就显示说明页。

### 纯函数：embedCheck.ts

[文件第 1 行](../src/embedCheck.ts#L1) 的注释很重要：**这个文件不能 import vscode**。因为 [scripts/verify-recommended.js](../scripts/verify-recommended.js) 会在 VS Code 之外直接 `require` 它的编译产物；一旦 import 了 vscode，那个脚本就会崩溃。（[recommended.ts 第 1 行](../src/recommended.ts#L1) 同理，只能 `import type`。）

- [EmbedVerdict，第 3 行](../src/embedCheck.ts#L3) 有四种结果：
  - `ok`：可以嵌入
  - `blocked`：响应头禁止嵌入
  - `insecure`：http 页面（混合内容）
  - `unknown`：请求失败或超时
- [verdictFromHeaders，第 9 行](../src/embedCheck.ts#L9)：
  - `X-Frame-Options` 是 `deny` 或 `sameorigin` → blocked（[第 11–14 行](../src/embedCheck.ts#L11)）。`allow-from` 浏览器早已废弃，不算。
  - CSP 里有 `frame-ancestors` 且不含 `*` → blocked（[第 16–24 行](../src/embedCheck.ts#L16)）。多条策略用逗号分隔，指令用分号分隔，所以是两层循环。
- [checkEmbeddable，第 32 行](../src/embedCheck.ts#L32)：
  - `http:` 开头直接 `insecure`，不用请求（[第 34–36 行](../src/embedCheck.ts#L34)）。
  - 发 GET 请求，**只要响应头，不下载正文**（[第 40 行](../src/embedCheck.ts#L40) 取消 body）。
  - 重定向后落到 http 也算 insecure（[第 41–44 行](../src/embedCheck.ts#L41)）。
  - 超时 8 秒（[第 38 行](../src/embedCheck.ts#L38)），**任何异常都是 `unknown`**（[第 46–48 行](../src/embedCheck.ts#L46)）。`unknown` 当作可以嵌入：宁可让用户看到空白，也不要因为一次网络抖动就错误地拦下一个能用的网站。
- [FetchLike，第 6 行](../src/embedCheck.ts#L6)：把 `fetch` 抽象成一个函数类型，测试时传假的，不用联网。

### 带缓存的检测器：embedChecker.ts

[EmbedChecker](../src/embedChecker.ts#L5) 包一层缓存和事件：

- `results`（已有结果）和 `pending`（正在进行的请求）两个 Map（[第 6–7 行](../src/embedChecker.ts#L6)）。
- [check，第 17 行](../src/embedChecker.ts#L17)：有结果直接返回；有进行中的请求就**共用同一个 Promise**（[第 22–24 行](../src/embedChecker.ts#L22)），所以同一个网址不会并发请求两次；完成后写缓存、触发 `onDidChange`（[第 26–28 行](../src/embedChecker.ts#L26)）——树视图正是靠这个事件才知道要刷新 ⚠。
- [clear，第 36 行](../src/embedChecker.ts#L36)：⟳ 刷新时清缓存。缓存只在内存里，重启后重新检测（这是 spec 第 7 节的决定）。

### ❼ 对照：参考项目的 proxy.ts

参考项目为了绕过 iframe 限制，写了一个本地 HTTP 代理（[proxy.ts](../../urlNavigation/src/server/proxy.ts)）去改写网页内容。需要说明的是：在参考项目里，`extension.ts` 的 `start()` 调用已经被注释掉了，这个代理其实处于**关闭状态**。但它的写法有一串问题：

- **原项目**：
  1. `listen(port)` 没写主机，监听**所有网卡**，局域网里任何人都能把你的机器当开放代理；
  2. 对流式返回的数据块（chunk）直接做正则替换，标签恰好被切在两个块中间就会漏替换或破坏；
  3. 不处理 gzip，却把原响应的 `content-length` 原样复制过来，长度对不上；
  4. 只支持 GET；
  5. 用一个全局变量 `refererUrl` 记录“当前页”，两个页面同时请求就串了；
  6. `deactivate` 时没有关闭服务器。
- **现在**：**根本没有代理**。我们不改写网页，而是先检测、不能嵌入的就老老实实告诉用户并提供“在浏览器中打开”。所以上面 6 个问题一个都不存在。
- **为什么**：绕过网站自己的安全设置，既做不干净（登录态、脚本、相对路径、gzip……每一项都是坑），也带来安全风险。**做不到的事，诚实地告诉用户，比做一个有隐患的“能用”方案好。**说明页里那句“这是它自己的安全设置，插件没有办法绕过”（[html.ts:37](../src/html.ts#L37)）就是这个态度。

## 7. Webview：sitePanel.ts、html.ts、media/

### 单例面板

[SitePanel](../src/sitePanel.ts#L10) 用一个静态变量 [`current`（第 11 行）](../src/sitePanel.ts#L11) 保证编辑器里**始终只有一个标签页**，标题固定为 `README.md`（[第 22 行](../src/sitePanel.ts#L22)；这是参考项目就有的“摸鱼”设计，并且为什么只开一个标签页见 spec 第 7 节：标题全都叫 README.md，开多个就分不清了）。

[show，第 15 行](../src/sitePanel.ts#L15)：

- 已有实例：[`reveal`](../src/sitePanel.ts#L18) 把它带到前台；
- 没有：[创建面板](../src/sitePanel.ts#L20) 并注册监听（见 ❺）；
- 最后无论哪种，[更新 site 并重新渲染](../src/sitePanel.ts#L42)（这里每次都重新设置 `webview.html`，所以换网站时内容会刷新）。

[retainContextWhenHidden: true（第 26 行）](../src/sitePanel.ts#L26)：切到别的标签页再切回来，网页不会重新加载。代价是内存占用更大，但对“一个网页导航”是值得的。

### ❻ CSP 和 localResourceRoots

- **原项目**：Webview 没有 CSP，也没有 `localResourceRoots`——默认情况下，Webview 可以读取整个工作区和扩展目录的文件，页面里随便一段脚本想做什么都可以。
- **现在**：
  - [localResourceRoots（第 28 行）](../src/sitePanel.ts#L28)只放行 `extensionUri/media` 一个目录；
  - 两种页面都带 `<meta http-equiv="Content-Security-Policy">`：
    - iframe 页（[html.ts:18](../src/html.ts#L18)）：`default-src 'none'; frame-src https:; style-src ${cspSource} 'unsafe-inline';`。默认全部禁止，只开 `frame-src https:`，和 `insecure` 判定保持一致（这里甚至**不允许任何脚本**，因为 iframe 页根本不需要）；`style-src 'unsafe-inline'` 只是为了页面里那一小段内联样式。
    - 说明页（[html.ts:51](../src/html.ts#L51)）：`default-src 'none'; style-src ${cspSource}; script-src 'nonce-${nonce}';`——脚本只有带上 nonce 的那一个能运行。
- **为什么**：Webview 本质是一个浏览器页面，要按“里面可能有不可信内容”来对待（我们的 iframe 就是别人的网页）。**默认拒绝，再按需开洞**，是最稳的写法。
- 输出前的转义：网址和主机名放进 HTML 前都经过 [escapeHtml，第 6 行](../src/html.ts#L6)（[第 30 行](../src/html.ts#L30)、[第 52 行](../src/html.ts#L52)、[第 61 行](../src/html.ts#L61)），用户输入的名称/网址里就算有 `"><script>` 也破坏不了页面。有测试：[html.test.ts:25](../src/test/html.test.ts#L25)。

### nonce

[sitePanel.ts:56](../src/sitePanel.ts#L56) 每次渲染用 `crypto.randomBytes(16)` 生成一次性的随机串，同时写进 CSP 的 `script-src 'nonce-xxx'` 和 `<script nonce="xxx">`（[html.ts:72](../src/html.ts#L72)）。网页里即使被注入了别的 `<script>`，因为拿不到这个 nonce，也跑不起来。**nonce 必须每次不同**，所以放在 `render` 里，而不是写成常量。

### ❷ 资源路径

- **原项目**：[webView.ts:12](../../urlNavigation/src/classes/webView.ts) `Uri.file(join(__filename,'..','..','src','views'))`——用当前文件的位置往上爬再往下找 `src/views`。这依赖一个**没有写出来的前提**：打包后的 `dist/extension.js` 和源码目录的相对关系恰好是这样。一旦换了打包方式，路径就悄悄错了；而且它的 `.vscodeignore` 先排除了 `src/**`，又用 `!**/*.js`、`!**/*.png` 之类的规则把里面的资源“捞”回来，两处必须互相配合才不会漏文件。
- **现在**：[sitePanel.ts:28](../src/sitePanel.ts#L28) 和 [第 50 行](../src/sitePanel.ts#L50) 都是 `Uri.joinPath(context.extensionUri, 'media', ...)`，再通过 `webview.asWebviewUri(...)` 转成 Webview 能访问的地址。运行时要用的资源（[panel.css](../media/panel.css)、[panel.js](../media/panel.js)、[图标](../media/activitybar.svg)）全放在 `media/`。
- **为什么**：`extensionUri` 是 VS Code 直接告诉你的“插件安装在哪”，不管是开发模式、打包后、还是安装到别人电脑上都对。**放哪是约定出来的（media/），不是从文件位置推出来的。**`.vscodeignore` 里排除了 `src/**`，而 `media/` 会被保留（只排除了 [media/icon.svg](../.vscodeignore)，因为市场图标用的是 png）。

### ❹ 先 postMessage 再设 html

- **原项目**：[webView.ts:36–37](../../urlNavigation/src/classes/webView.ts) 先 `postMessage({label, website})`，下一行才设置 `webview.html`。此时页面还没加载，脚本里的 `message` 监听器还没注册，**消息发给了一个还不存在的接收方**，能不能收到取决于 VS Code 内部的缓冲（运气）。
- **现在**：**首次渲染根本不靠消息**。需要的数据（网址、主机名、原因文案、是否可移除）在 [render](../src/sitePanel.ts#L47) 里直接写进生成的 HTML（[html.ts:42](../src/html.ts#L42) 的 `buildExplanationHtml` 和 [html.ts:16](../src/html.ts#L16) 的 `buildIframeHtml`）。页面一出现就是完整的。
- **为什么**：“首次打开时直接把数据写进 HTML”是最简单、最不会出错的做法——不需要握手，也不存在时序问题。消息通信只留给**页面加载之后才发生**的事（用户点链接）。

### 消息通信：说明页上的三个操作

说明页里的链接不能直接执行 VS Code 命令（Webview 是沙盒里的网页），要靠消息：

1. 页面里的脚本 [media/panel.js](../media/panel.js)：`acquireVsCodeApi()`（[第 2 行](../media/panel.js#L2)）拿到通信对象；给每个带 `data-action` 的链接绑定点击，`preventDefault()` 后 `postMessage({ type: 动作名 })`（[第 3–8 行](../media/panel.js#L3)）。**页面里不放任何业务逻辑**，只做“把点击转成消息”。
2. 插件里 [handleMessage，第 65 行](../src/sitePanel.ts#L65) 收到后按 `type` 分发：
   - `openExternal` → `vscode.env.openExternal`
   - `copy` → 写剪贴板并提示
   - `remove` → 执行 `webNav.remove` 命令（[第 76 行](../src/sitePanel.ts#L76)），**只有它返回 true（用户确认且删除成功）才关闭面板**（[第 77–79 行](../src/sitePanel.ts#L77)）。这样“取消”不会把用户的页面白白关掉。

注意 `remove` 这个链接是否出现，由 `removable` 决定（[html.ts:55](../src/html.ts#L55)），推荐网站的说明页上没有它，因为推荐的网站不是用户自己添加的（[sitePanel.ts:54](../src/sitePanel.ts#L54) 传入 `source === 'mine'`）。

### 说明页自动适配浅色/深色主题

[media/panel.css](../media/panel.css) 里**没有写任何颜色值**，全部使用 VS Code 注入的主题变量，例如 [`--vscode-foreground`](../media/panel.css#L7)、[`--vscode-descriptionForeground`](../media/panel.css#L22)、[`--vscode-textLink-foreground`](../media/panel.css#L29)。主题一换，变量跟着变，说明页自然就跟着变，不需要任何额外代码。还有个测试专门检查没有硬编码颜色：[html.test.ts:30](../src/test/html.test.ts#L30)。

## 9. 打包

### esbuild 替代 webpack

[esbuild.js](../esbuild.js) 只有 56 行，关键配置：

- [入口 `src/extension.ts`，第 28–30 行](../esbuild.js#L28)，输出 [`dist/extension.js`，第 37 行](../esbuild.js#L37)；
- [`format: 'cjs'`、`platform: 'node'`，第 32、36 行](../esbuild.js#L32)：扩展宿主是 Node，用 CommonJS；
- [`external: ['vscode']`，第 38 行](../esbuild.js#L38)：`vscode` 模块是 VS Code 在运行时提供的，不能打进去（和参考项目的 webpack externals 同理）；
- 生产模式压缩，开发模式带 sourcemap（[第 33–34 行](../esbuild.js#L33)）。

和 webpack 相比：不需要 `ts-loader`，也不需要 `webpack.config.js` 里一大堆 loader 配置，速度快一个数量级。注意：**esbuild 只负责转译，不检查类型**，所以类型检查另外跑 `tsc --noEmit`（[package.json:208](../package.json#L208)）。`package` 脚本（[第 204 行](../package.json#L204)）是“类型检查 → lint → 生产构建”三步，`vscode:prepublish`（[第 199 行](../package.json#L199)）会在 `vsce package` 之前自动调用它，所以打包前一定检查过类型。

### .vscodeignore

[.vscodeignore](../.vscodeignore) 决定 vsix 里**不放**什么：源码（`src/**`）、测试产物（`out/**`）、`docs/**`、`scripts/**`、配置文件、`node_modules/**`、sourcemap。因为插件已经打成了单个 `dist/extension.js`，运行时不需要 node_modules。留下的就是 `dist/`、`media/`、`package.json`、README、LICENSE。

### 打包命令

```
npx @vscode/vsce package
```

发布必须有 `publisher`，它是你在应用市场创建的 publisher ID（这里是 `manaster`），和 `name` 拼成插件的唯一 ID `manaster.web-nav`。spec 第 7 节规定它必须由你本人提供，所以开发时一直空着，等你创建了 publisher 才填上。详细步骤见 [发布步骤.md](发布步骤.md)。

## 11. Claude 替你做的决定（你可以推翻）

下面这些，是在设计和计划阶段你没有明确表态、由我（Claude）拍板的，随时可以改。

### 设计阶段（spec 第 7 节）

1. **项目名称**：目录名和 `name` 暂定 `web-nav`，`displayName` 是“网站导航”。发布前可以改；`publisher` 必须由你提供。
2. **添加网站的流程**：点 ＋ → 输入网址（校验必须是 http/https）→ 输入名称（默认填域名）→ 保存到设置 → 后台检测并刷新标记。（[addSite](../src/commands.ts#L76)）
3. **“我的网站”的右键操作**：在浏览器中打开、复制链接、重命名、修改网址、移除。（[package.json:159](../package.json#L159)）
4. **“推荐”网站的右键操作**：在浏览器中打开、添加到我的网站；另有设置项 `webNav.showRecommended` 可以隐藏整个推荐分组。（[package.json:43](../package.json#L43)；[isRecommendedVisible](../src/sites.ts#L88)）
5. **推荐网站按类别分子组**：学习、面试刷题、博客、阅读。（[recommended.ts](../src/recommended.ts#L10)）
6. **标签页始终只有一个**：点别的网站就在同一个标签页里切换；标题固定 `README.md`，开多个会分不清；开启 `retainContextWhenHidden`，切回来不重新加载。（[sitePanel.ts:11](../src/sitePanel.ts#L11)、[第 26 行](../src/sitePanel.ts#L26)）
7. **检测结果缓存在内存里**：点 ⟳ 重新检测；添加时检测一次；打开时没有结果就先检测。（[embedChecker.ts](../src/embedChecker.ts#L5)、[extension.ts:29](../src/extension.ts#L29)）
8. **http:// 网站的处理**：添加时先试 https，能通就自动改用 https；不能就照样保存，打开时显示说明页，原因换成“这个网站只支持不加密的 http 连接……”。推荐列表里只放 https 网站。（[tryUpgradeToHttps](../src/embedCheck.ts#L52)、[REASON_TEXT.insecure](../src/html.ts#L38)）
9. **Webview 安全**：CSP（`frame-src` 只允许 https，脚本用 nonce），`localResourceRoots` 只开放 `media/`。（第 7 节）
10. **测试策略**：判断逻辑写成纯函数做单元测试，再加一个冒烟测试确认插件能激活、命令都注册。（第 8 节）
11. **LICENSE 用 MIT**，README 里说明受“常用网站RSS”（zw990316/urlNavigation）启发。

### 计划阶段新增的决定

12. **不带协议时补 https**：输入 `www.runoob.com` 自动变成 `https://www.runoob.com/`。（[normalizeUrl](../src/sites.ts#L19)）
13. **激活后在后台检测**：不阻塞激活，结果回来时树自己刷新 ⚠。（[extension.ts:40](../src/extension.ts#L40)）
14. **移除前确认**：模态对话框，用户确认才删除；说明页上的“从列表中移除”也走同一个命令，取消时不关闭面板。（[commands.ts:194](../src/commands.ts#L194)、[sitePanel.ts:76](../src/sitePanel.ts#L76)）
15. **favicon 的处理方式**：默认显示 Codicon 地球图标（spec 第 5.1 节要求拿不到时回退）；对每个站点的 `origin/favicon.ico` 探测一次，只有响应成功且是 `image/*` 才换成远程图标，结果按地址缓存，⟳ 刷新时清空。这是终审时从“全有或全无”的简单方案改成的。（[siteTree.ts:100](../src/siteTree.ts#L100)、[favicon.ts](../src/favicon.ts#L19)、[faviconChecker.ts](../src/faviconChecker.ts#L5)）
16. **保存前重新读取设置**（一个后来发现问题后加的决定）：所有写设置的命令都经过 [saveFresh](../src/commands.ts#L59)，避免用过期快照覆盖别处的修改。
